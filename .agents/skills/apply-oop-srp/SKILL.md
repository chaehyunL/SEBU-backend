# 객체지향 설계와 SRP 적용

## 작성 정보

- 작성일: 2026-08-13
- 작성한 Skill: `apply-oop-srp`
- 작성 내용: SEBU 백엔드의 기능 구현과 리팩터링 과정에서 객체지향 설계와 단일 책임 원칙(SRP)을 적용하고, 책임 경계와 의존성 방향을 점검하며 과잉 설계를 방지하는 Skill을 작성했다.
- 상세 기록 파일: [references/2026-08-13-apply-oop-srp.md](references/2026-08-13-apply-oop-srp.md)

요청한 동작을 명확한 책임과 저장소의 기존 구조에 맞는 최소한의 추상화로 구현한다. SRP를 클래스당 메서드 하나가 아니라 하나의 변경 이유로 해석한다.

설계를 결정하기 전에 [references/2026-08-13-apply-oop-srp.md](references/2026-08-13-apply-oop-srp.md)를 읽는다. 참조 문서와 현재 코드가 다르면 관련 운영 코드와 테스트를 기준으로 판단한다.

## 작업 절차

### 1. 변경 경계 파악

- 요청한 동작, 관련 사용자, 입력, 출력, 불변 조건, 실패 사례를 식별한다.
- 인접한 Controller, Application Service, 도메인 객체, Repository, Projection, DTO, 테스트를 확인한다.
- 영향을 받는 각 타입의 현재 책임을 한 문장으로 설명한다.
- 요청과 무관한 아키텍처와 동작은 변경 범위에서 제외한다.

### 2. 책임 배치

각 책임을 가장 좁고 적절한 경계에 배치한다.

- HTTP 요청 처리, 입력 검증, 상태 코드 선택, 응답 변환은 `api`에 둔다.
- 유스케이스 조정, 트랜잭션 경계, Repository 협력, 인가 흐름은 `application`에 둔다.
- Entity나 Value가 소유하는 비즈니스 불변 조건과 상태 전이는 `domain`에 둔다.
- 영속성 조회와 데이터베이스 접근 세부 사항은 Repository 또는 Projection 뒤에 둔다.
- 인증과 Rate Limit은 기존 Cross-cutting 패키지에 유지한다.

새로 만들거나 변경하는 각 타입의 변경 이유를 식별한다. 서로 다른 이유로 변경되거나, 독립적인 테스트가 필요하거나, 명확한 의존성 경계가 있을 때만 타입을 분리한다. 같은 이유로 변경되는 응집도 높은 동작은 함께 유지한다.

### 3. 객체 설계 점검

- 의존성 방향을 유지한다. `api`는 `application`에 의존할 수 있고, `application`은 `domain`에 의존할 수 있지만, `domain`은 `api`에 의존하지 않는다.
- 생성자 주입과 명시적인 의존성을 우선한다.
- 변경 가능한 상태를 노출하지 말고 유효한 상태 전이를 캡슐화한다.
- 상속이 실제 하위 타입 관계를 나타내지 않으면 합성을 우선한다.
- 공개 API를 유스케이스에 필요한 최소 범위로 제한한다.
- 실제 경계, 의미 있는 대체 구현, 기존 저장소 관례가 있을 때만 Interface를 도입한다.
- 기술적 처리 단계보다 도메인 의도를 나타내는 이름을 사용한다.

### 4. 작고 응집도 높은 변경 구현

- 기존 패키지 구조, Annotation, 트랜잭션 관례, 예외 처리 방식, 명명법을 따른다.
- 기존 추상화의 책임에 새 동작이 실제로 포함될 때만 재사용한다.
- 책임을 명확하게 설명할 수 있고 기존 소유자가 없을 때만 새 타입을 추가한다.
- 설계를 이론적으로 완벽해 보이게 만들기 위한 목적으로 기존 동작을 이동하지 않는다.
- 요청과 무관한 정리 작업을 함께 수행하지 않는다.

### 5. 잘못된 SRP 적용과 과잉 설계 방지

다음 행동을 하지 않는다.

- 메서드나 작은 작업마다 별도 클래스를 생성한다.
- 정책이나 동작을 소유하지 않는 단순 위임 Wrapper를 추가한다.
- 구체적인 경계 없이 모든 Service와 Repository에 Interface를 생성한다.
- 가상의 미래 요구사항을 위해 Factory, Strategy, Event, 상속 구조를 도입한다.
- 코드 줄 수를 줄이기 위해 하나의 응집된 트랜잭션을 여러 Service로 나눈다.
- Controller, Service, Entity에 동일한 도메인 규칙을 중복한다.

두 설계가 모두 유효하면 개념 수가 적고 변경 책임이 더 명확한 설계를 선택한다.

### 6. 동작과 경계 검증

- 요청한 동작, 주요 실패 사례, 도메인 불변 조건을 검증하는 테스트를 추가하거나 수정한다.
- 동작을 소유하는 가장 좁은 계층에서 테스트하되, 필요한 경우 저장소의 기존 통합 테스트 방식을 유지한다.
- Unix 계열에서는 `./gradlew test`, Windows에서는 `.\gradlew.bat test`를 실행한다.
- Diff를 다시 읽고 변경된 모든 타입에 설명 가능한 하나의 변경 이유가 있는지 확인한다.
- 순환 의존성이 새로 생기지 않았고 영속성 및 HTTP 세부 사항이 Domain으로 유출되지 않았는지 확인한다.
